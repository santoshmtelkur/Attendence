# Deploying to Render

This project now includes a `render.yaml` **Blueprint** at the repo root. It tells Render to
create three things together, already wired to each other:

1. `attendance-db` — a managed Postgres database
2. `attendance-backend` — the Spring Boot API (built from `backend/Dockerfile`)
3. `attendance-frontend` — the React app (built as a static site)

You do **not** need to manually create the database, set the JDBC URL, or configure CORS/JWT —
the Blueprint does all of that. Only a couple of things need you.

---

## 1. Push this project to GitHub

Render deploys from a Git repo, not a zip upload. From the unzipped project folder:

```bash
cd college-attendance-system
git init
git add .
git commit -m "Initial commit"
```

Then create a new **empty** repo on GitHub (no README/license), and:

```bash
git remote add origin https://github.com/<your-username>/<your-repo>.git
git branch -M main
git push -u origin main
```

## 2. Deploy the Blueprint on Render

1. Go to the Render dashboard → **New** → **Blueprint**.
2. Connect the GitHub repo you just pushed.
3. Render reads `render.yaml` automatically and shows you the 3 resources it's about to create.
4. It will ask you to fill in **`MAIL_USERNAME`** and **`MAIL_PASSWORD`** at this step — see
   §3 below. You can leave both blank for now and fill them in later; the app works fine
   without them (email sending is off by default).
5. Click **Apply**. First deploy takes a few minutes (Postgres provisions, then the backend
   Docker image builds, then the frontend builds).

That's it — no manual env var wiring, no manual DB creation.

---

## 3. What you can fill in manually (all optional)

Everything below already has a safe default baked into `render.yaml`, so the app runs
correctly with **zero** manual input. These are only for turning on real behavior later.

| Variable | Where | Default in render.yaml | What it's for | Fill in only if... |
|---|---|---|---|---|
| `MAIL_ENABLED` | Backend service → Environment | `false` | Turns real email sending on/off | You want real absence/digest emails sent |
| `MAIL_USERNAME` | Backend service → Environment | *(blank)* | SMTP login | `MAIL_ENABLED=true` |
| `MAIL_PASSWORD` | Backend service → Environment | *(blank)* | SMTP password / app password | `MAIL_ENABLED=true` |
| `MAIL_HOST` | Backend service → Environment | `smtp.gmail.com` | SMTP server | You're not using Gmail |
| `MAIL_PORT` | Backend service → Environment | `587` | SMTP port | You're not using Gmail |
| `MAIL_FROM` | Backend service → Environment | `attendance-noreply@college.edu` | "From" address on outgoing mail | You want a different sender address |
| `JWT_SECRET` | Backend service → Environment | auto-generated by Render | Signs login tokens | You want to set your own instead of the generated one |
| `LOW_ATTENDANCE_THRESHOLD` | Backend service → Environment | `75` | % below which a student is "low attendance" | Your college uses a different cutoff |
| `SEED_DEMO_DATA` | Backend service → Environment | `true` | Seeds demo departments/students on first run | Set to `false` once you've added your real data, to stop it trying to reseed |

**To turn on real email (Gmail example):**
1. Enable 2-Step Verification on the Gmail account you want to send from.
2. Generate an [App Password](https://myaccount.google.com/apppasswords) (not your normal Gmail password).
3. In Render → `attendance-backend` → Environment, set:
   - `MAIL_ENABLED` = `true`
   - `MAIL_USERNAME` = your Gmail address
   - `MAIL_PASSWORD` = the 16-character App Password
4. Save — Render redeploys automatically with the new values.

If you use a different email provider (SendGrid, Mailtrap, Brevo, your college's own SMTP,
etc.), just change `MAIL_HOST` / `MAIL_PORT` / `MAIL_USERNAME` / `MAIL_PASSWORD` to match — no
code changes needed.

## 4. After the first deploy

- Backend URL: `https://attendance-backend.onrender.com`
- Frontend URL: `https://attendance-frontend.onrender.com`
- Health check: `https://attendance-backend.onrender.com/actuator/health` should return `{"status":"UP"}`
- Log in with the seeded demo accounts: `admin` / `admin123`, or `CSE21001` / `password123`

**Free tier notes** (not errors — just how Render's free plan behaves):
- Free web services spin down after ~15 minutes of no traffic and take ~30–60s to wake up
  on the next request — the first request after idling will feel slow, that's normal.
- Free Postgres databases on Render expire after 90 days unless upgraded to a paid plan —
  you'll get an email warning before that happens.
- Once you're past evaluating and have real student/faculty data, set `SEED_DEMO_DATA=false`
  so a restart never re-seeds demo rows into your real data.

## 5. If you'd rather not use the Blueprint

You can still create the two services and the database manually in the Render dashboard —
`render.yaml` is just automation for exactly that. If you do it manually, the important part
is setting the backend's `DB_HOST`, `DB_PORT`, `DB_NAME`, `DATABASE_USERNAME`,
`DATABASE_PASSWORD` env vars from your Postgres instance's "Connection" tab (not the
JDBC-style `DATABASE_URL`, since Render's dashboard doesn't provide one in that format).
